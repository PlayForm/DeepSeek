Just click "OK"

Understanding that this change may effectively be as simple as clicking "OK" to a pop-up, I am asking for a mechanism (such as the PNA server-side opt-in) that allows some form of suppression to this pop-up that doesn't involve side-loading an enterprise policy for any and all browsers enforcing this requirement.

In regards to the QZ Tray example above, we already make our users click OK so this is a pop-up to see a pop-up. 😅

Edit: Maybe this is more of a gentle ask to provide end-user policies? This isn't the first browser policy we've battled, but a mechanism to pre-allow on the client-end would be a welcome-change.

  • Provide a mechanism for whitelisting #38

How to supply "targetAddressSpace" to WebSocket connection?

For any of the WebSocket services running on localhost, no changes are needed, however for public DNS addresses that point to local addresses, this will be a new requirement. The specification explains how this is provided to fetch(), but how will it be provided to WebSocket?

    I think it might help clarify things to split this into two pieces.

    First, any request from a public site that connects to a local or loopback IP address will trigger the LNA permission prompt. This is based on the resolved IP address after trying to make the connection. Being able to get the LNA permission is additionally gated on the site being a secure context (i.e., served over HTTPS).

    Second, because sites that need the LNA permission must be HTTPS, but local network requests are often to devices where it is currently difficult to get working HTTPS and if accessed over HTTP they would ordinarily be blocked as mixed content, the LNA permission additionally relaxes the mixed content blocking logic to allow certain local network requests through.

    So for your WebSocket use case there are four examples I can work through:

    1. If the public website connecting to the local QZTray software does it using the URL ws://127.0.0.1:8080/..., this would not count as mixed content (as localhost is considered a secure context) but would trigger the LNA permission prompt.
    2. If the public website connecting to the local QZTray software does it using the URL ws://192.168.0.10:8080/... (where 192.168.0.10 is the internal IP address of the machine running the software), this would be automatically exempted from mixed content checks (because the hostname is an internal IP address), and would trigger the LNA permission prompt.
    3. If the public website connecting to the local QZTray software does it using the URL ws://internal.example.com:8080/... (where internal.example.com resolves to either 127.0.0.1 or 192.168.0.10), this would be blocked as mixed content (because the mixed content checker triggers before hostname resolution)
    4. If the public website connecting to the QZTray software does it using the URL wss://internal.example.com:8080/... (where internal.example.com resolves to either 127.0.0.1 or 192.168.0.10 and that machine has a trusted HTTPS certificate), this would not count as mixed content but would trigger the LNA permission prompt.

    If we were able to add something akin to the targetAddressSpace fetch() option but for WebSockets, that would be useful for Example 3 above -- it would allow the public website to "pre-declare" that the hostname would resolve to a local address, allowing the mixed content checker to exempt the request. It would have no effect in the other three cases.
